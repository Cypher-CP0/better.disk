Better Disk Manager Windows Product and Technical Specification

Version 0.1 · 9 October 2026 · Proposed implementation baseline

Build a Windows desktop disk manager that scans local storage, presents a green treemap and searchable list, compares locally saved scans, and supports reviewed recycling of eligible personal files. This specification is the implementation contract for version 1. The accompanying design document defines layout and user journeys.

MUST indicates a release requirement. SHOULD indicates a preferred implementation that may change with documented evidence. Proposed performance figures are engineering targets, not measured results. The selected stack is a recommendation to validate in an initial prototype.

1 Platform and scope

The initial supported target is Windows 11 x64, running as the current user. Test on the latest supported Windows 11 releases available when packaging. Windows 10, ARM64, macOS, Linux, network shares, and MTP devices are outside the first support matrix. Do not reject or change operating-system settings to improve scan speed.

Support local NTFS drives as the primary filesystem and local exFAT removable drives for scanning. Enable recycling only on a target where the tested Windows adapter can enforce recycle-only behavior. Removable-drive uncertainty must disable cleanup without disabling read-only analysis.

2 Functional requirements

FR01 Choose and scan a location

MUST enumerate eligible local volumes and allow a Windows folder picker. Resolve volume identity and scan root before starting. A single scan runs at a time; changing the scan root requires cancelling or completing the current scan. Browsing saved scans remains available during scanning.

The scanner MUST enumerate metadata without reading file contents. It MUST report discovered file and directory counts, elapsed time, current location, warnings, and measured bytes. Total item count is unknown during discovery, so progress MUST remain indeterminate. Deliver batched progress at no more than five updates per second and keep enumeration off the UI thread.

Cancellation MUST stop scheduling work, drain or cancel pending tasks, and retain a clearly labeled partial result. Do not call cancelled scans complete. Permission failures MUST be recorded per path and MUST NOT abort unrelated readable subtrees. No automatic elevation or privileged background service is included.

FR02 Account for storage honestly

Store logical file length separately from measured allocation. Query appropriate Windows allocation metadata, including compressed or sparse allocation where supported [S3]. If allocation cannot be measured, store null with a reason; do not silently substitute logical bytes in Size on disk mode.

Identify hard links by volume identity and file ID. Count allocation once per unique identity in the root total. For additive folder maps, assign counted bytes to the lexicographically first relative path using a stable Windows ordinal comparison and mark other entries as aliases. Retain full logical length and measured allocation in entry details, plus separately stored counted allocation. If identity is unavailable, disclose that deduplication is unverified. The representation does not establish how many bytes deleting a link will reclaim [S4].

Query drive capacity, free bytes, and bytes available to the current user independently [S6]. Do not force scanned totals to match used capacity. Display any positive gap as Unaccounted space, with possible filesystem metadata, restricted locations, or other allocation causes. If measured totals exceed reported used space due to changes during scanning or shared-storage uncertainty, display a discrepancy rather than a negative gap.

Size on disk is measured allocation, not a guarantee of physically unique blocks or reclaimable space. Version 1 does not measure every filesystem metadata structure, alternate data stream, or storage-provider sharing mechanism. Coverage notices MUST explain relevant uncertainty.

FR03 Handle special paths

Do not traverse directory junctions, symbolic links, or mounted-volume reparse points in version 1. Record them as link entries; exclude target contents from totals and disable cleanup of link entries. Detect cloud-provider placeholders separately, using Windows attributes and provider-aware metadata where required [S5]. Metadata inspection MUST NOT deliberately hydrate or download online-only content. Allocation remains unknown when it cannot be established without hydration.

Support Unicode, deep paths, long paths permitted by Windows, case-sensitive directories, concurrent file changes, and drive disconnection. Preserve path spelling. Do not merge distinct paths solely by converting them to lowercase. A path whose metadata cannot be decoded for display still requires an internal Windows-native representation; a lossy display string cannot become the action target.

FR04 Show a synchronized map and list

MUST render immediate children at the current navigation level using a deterministic squarified treemap. Folder values aggregate matching descendant files. Map and list MUST share filters, metric, selection, and scan ID. Cap displayed rectangles at 1,500, aggregating small entries into navigable groups. Virtualize list rows and query pages of at most 200 items.

Percentages MUST use the known bytes of the current filtered result. Show unknown-allocation count beside totals. Zero-byte entries are visible in the list. In logical mode, hard-link paths count as separate named file lengths and the interface MUST disclose that the metric is File size, not unique storage.

FR05 Search and filter

MUST support case-insensitive name/path search for user convenience, without changing path identity. Search is literal text, not shell syntax or regular expressions. Minimum size uses the currently selected size metric on individual file entries. Unknown allocated size fails a positive allocated-size threshold but remains available through an Unknown size filter. Type/category and date filters intersect with search and size.

Use bytes internally. Display decimal B, KB, MB, GB, and TB, where 1 GB is 1,000,000,000 bytes. Allow explicit GiB input, where 1 GiB is 1,073,741,824 bytes. Show exact bytes in details. Validate negative, invalid, and overflowing inputs; do not truncate silently. Folder aggregates MUST be recomputed from the filtered files.

FR06 Color by a defined date metric

Default to modification age. Access age is optional within the interface and MUST show its limits: Windows timestamps may be disabled, delayed, or reflect background access [S1]. Never infer an access count from a timestamp. Reliability values are Known, Unverified, or Unavailable. Unverified access dates render as Unknown unless the user explicitly chooses to include them with a persistent notice. Checking reliability MUST NOT alter the filesystem's access-time policy.

Compute age from scan start in UTC, with boundaries of 7, 30, 90, and 365 elapsed 24-hour days. Negative age, missing dates, and invalid dates are Unknown. Save the reference time in the snapshot. For aggregate blocks, choose the bucket containing the greatest counted bytes; break ties toward the most recent known bucket. Unknown participates as a bucket and wins when strictly largest; ties with Unknown choose Unknown conservatively. Details MUST expose the distribution and metric provenance.

FR07 Identify categories and apps

File type classification uses a versioned extension mapping. Downloads uses Windows Known Folder location membership. Categories are alternative filters and can overlap; category totals MUST NOT be added together as a drive total. Directory names alone MUST NOT establish app ownership.

Apps grouping SHOULD use installed-app metadata and explicit installation roots obtained through Windows APIs or documented registry locations. Ignore advertised install sizes as measurements. Only uniquely attributed scanned installation paths count toward a group. Shared and ambiguous locations remain unattributed. Missing roots and inaccessible content show Partial coverage. No claim to complete app storage, and no deletion of an app group, is allowed.

FR08 Save and compare scans

Saved scans MUST persist schema version, root, volume identity, configuration, exclusion set, size-accounting version, start/end time, warnings, and completeness. Autosave completed scans locally; cancelled scans require explicit Save partial scan. Default retention is 10 snapshots per root, with user-controlled deletion and a global 1 GB soft budget. If an additional save exceeds the budget, stop autosaving and offer review of history; do not silently erase snapshots.

Comparison MUST require matching volume/root and compatible accounting and exclusion settings. If identity, scope, or policy differs, block quantitative comparison with a reason. Complete comparable scans support additions, removals, confirmed renames, logical-size changes, and counted-allocation changes. Match stable identities where trustworthy and distinguish reused IDs using available creation metadata; otherwise use exact relative path as the fallback. Ambiguous matches are marked uncertain rather than called renames.

Incomplete scans can be compared only within subtrees confirmed fully covered by both scans. Disappearance inside an omitted subtree MUST NOT be reported as deletion. Comparison lists retain signed byte changes; a growth map uses positive deltas only, with a separate shrinkage list. Snapshot differences are observations between scans, not a log of every filesystem event.

FR09 Pin and exclude locations

Pinning prevents cleanup of an item and its descendants; it does not hide storage from scans. Scan exclusions omit subtrees from measurement and are shown in coverage. Store these as different settings. If a pinned item is renamed and its stable identity is recognized, keep its protection; otherwise retain the path rule and explain its scope.

The built-in protected cleanup set includes volume roots, the Windows directory, installed application directories, ProgramData, AppData, recovery/system locations, Recycle Bin internals, and the application's own storage. Resolve platform locations instead of assuming C drive paths. Protection covers recognized aliases and cannot be overridden in version 1.

FR10 Review and recycle personal files

Version 1 cleanup MUST operate on explicitly selected regular files owned by the current user within their Known Folder personal locations, or within an explicitly approved personal folder on a supported local drive. The backend MUST enforce this scope. Files in protected, unverified, or reparse-backed paths are ineligible. Recursive folder cleanup is deferred until full unfiltered enumeration and review are implemented.

Create a review plan from entry IDs, not arbitrary frontend paths. Display full paths, logical size, measured size, and eligibility reasons. Immediately before execution, revalidate volume, file identity, resolved path and ancestors, ownership, protection, metadata, and pin state. Changed or replaced targets MUST be skipped and require a new review. Reject path traversal and any target outside the approved scope.

Use Windows Shell IFileOperation with recycle-only behavior and per-item completion callbacks [S2]. Never fall back to permanent deletion. If recycling cannot be enforced, fail that item. Do not suppress a Windows warning that reveals permanent removal. Verification of large-file, unsupported-volume, and bin-capacity behavior is a release gate.

Operations are cancellable between submitted items; cancellation cannot promise reversal of an operation already accepted by Windows. Retain per-item succeeded, failed, skipped, and cancelled results. Record intended actions before invoking the Shell; after a crash, reconcile uncertain results rather than retrying them blindly. Path validation reduces races, but the Shell's path-based action is not an atomic identity-bound delete; restrict cleanup accordingly and document residual concurrent-change risk.

Recycling usually does not immediately free drive space. MUST report Bytes moved to Recycle Bin separately from a freshly queried available-space change. Other processes can affect free space, so that change MUST NOT be presented as exact reclaimed bytes. Recovery opens Windows Recycle Bin; in-app restoration and emptying the bin are excluded.

FR11 Settings and local privacy

MUST offer theme, display metric, exclusions, pins, snapshot retention, and clear history. No account, telemetry, startup agent, cloud upload, automatic update check, or network dependency is required for core use. Logs MUST omit full personal paths by default. Diagnostic export requires a preview and explicit user action. Clearing history removes scan metadata; uninstall offers whether to retain settings and history.

3 Proposed architecture

Use Tauri 2 for the desktop shell, React and TypeScript for the interface, Rust for scanning and filesystem operations, and SQLite for local metadata. Use a pure layout function for treemaps, with a Canvas renderer and an accessible HTML list. This preserves a path toward macOS while isolating Windows behavior. The tradeoff is Rust and Win32 integration complexity; benchmark and prototype these before committing to the stack.

Windows uses WebView2; development requires the relevant Tauri Windows prerequisites [S7]. Pin exact dependency versions and toolchains at project bootstrap rather than relying on floating latest versions.

The frontend MUST NOT receive broad filesystem write or shell execution permissions. Register explicit custom command permissions and restrict them to the bundled main window; do not assume Tauri's capability files automatically protect unrestricted custom handlers [S8]. Native methods perform their own scope validation. Disable remote application content and arbitrary navigation, use a restrictive content security policy, and escape all file names as text.

A bounded worker pool enumerates directories and collects metadata. Start with two workers and tune using SSD and removable-drive benchmarks. Batch database writes. Store full scan data in SQLite and return aggregates or pages to the frontend, not millions of entries in one JSON payload. Cancellation tokens, queue limits, and event throttling prevent memory growth and UI saturation.

5 Lifecycle and consistency

Scans move through Queued, Scanning, Finalizing, and Complete. Cancellation leads to Cancelled with partial coverage; an unrecoverable root or persistence error can lead to Failed while retaining readable results. Per-entry errors may result in Complete with omissions. Finalizing and publication occur transactionally; a snapshot is never advertised as complete before commit.

Cleanup plans move through Prepared, Revalidating, Running, and Finished or Cancelled. They expire after 10 minutes or whenever scope, protection, selection, or relevant metadata changes. A consumed plan cannot run twice. Incomplete operation records after restart appear as Requires reconciliation.

A scan observes a live filesystem and is not an atomic volume snapshot. Record changes detected during metadata reads and permit rescan. Each saved result retains its scan interval. Cleanup results trigger refresh of affected parents and the drive-space query; historical snapshots remain immutable.

6 Performance and accessibility targets

Use a documented baseline of Windows 11 x64, a four-core CPU, 16 GB RAM, and an SSD. Measure release builds with Defender enabled. Maintain a reproducible metadata dataset of 100,000 files and a larger 1,000,000-file fixture, recording depth, link count, and storage type. Do not advertise a full-drive scan time before measurement.

If scan-rate or memory targets fail, profile the bottleneck before adjusting the stack or enabling any privileged acceleration. Record measured results and any justified target revision. Accuracy, cleanup safeguards, and accessible operation are mandatory regardless of performance.

MUST support keyboard-only completion of primary workflows, Narrator-readable controls and list content, visible focus, system high contrast, reduced motion, and 100 to 200 percent Windows scaling. The Canvas map cannot be the only route to an item. Verify text and component contrast using the rendered UI, not palette values alone.

Unit tests should cover aggregation, filters, date bucketing, identity matching, plan expiry, and policy decisions. 8 Delivery stages and release gates

Stage 0 Windows feasibility prototype. Validate Rust metadata reads, hard-link accounting, cloud placeholders, WebView2 startup, accessible list behavior, and recycle-only Shell failures. Produce measurements and resolve stack risks before full UI implementation.

Stage 1 Read-only explorer. Implement root selection, enumeration, allocated/logical accounting, map/list, filters, date legend, and item details. Gate on AT01 through AT08 and path handling. No cleanup action is exposed yet.

Stage 2 History and grouping. Add persistence, comparisons, partial app grouping, pins and exclusions. Gate on AT09, AT10, AT16, and snapshot compatibility tests.

Stage 3 Reviewed personal file cleanup. Implement the scoped backend, plan validation, Shell callbacks, reconciliation, and result screen. Gate on every cleanup acceptance test. If recycle-only failure behavior is unproven, ship a read-only beta and keep cleanup disabled.

Stage 4 Windows beta package. Build a per-user installer, handle missing WebView2 through the documented installation flow, test install/uninstall on a clean machine, and include license notices. Verify performance, accessibility, offline behavior, and the five-user design review. Code signing and distribution channel selection are separate launch decisions; an unsigned build is labeled a development/beta artifact.

No fixed dates are assigned before the feasibility prototype establishes implementation effort. A public paid release requires completed mandatory tests, transparent support scope, a distribution decision, and a defined commercial model.

9 Deferred decisions

Validate installed-app attribution through representative Windows apps before expanding into cache recommendations. Benchmark generic enumeration before considering MFT-based acceleration. Determine billing, trials, signing budget, Windows 10/ARM64 support, and macOS scheduling after a working Windows beta. The downloads companion may later share file provenance and storage warnings through an explicit local interface; it must not complicate the first scan engine.
